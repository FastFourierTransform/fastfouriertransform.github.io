配置 Cloudflare WARP 节点分流解决 Gemini API 报错

2026/6/10 网络 Cloudflare

背景

为什么需要 Cloudflare Warp

恰如外卖大战给普通人送来了各种大额神券，大模型厂家之间的竞争也给普通人送来了免费的API，每天1500次的免费 gemini flash API 调用还是很诱人的。然而我现在使用的机场已经沦为了风险极高的公交车，直接访问会被当场墙掉，只能更换干净且受信任的机场，然而这也带来了两个全新的问题：一是不得不让我抛弃使用了6、7年的便宜且稳定的机场，二是寻找新的机场还要花费大量的时间和金钱试错，风险与收益不成正比。然后我发现可以利用 Cloudflare Warp 节点分流这一操作，来完美解决我的问题，我的便宜稳定机场可以继续正常使用，也可以美美白嫖 gemini API。

Cloudflare 是什么

Cloudflare（简称 CF）。它是全球最大的网络安全和 CDN（内容分发网络）巨头之一。全球有数千万个网站都托管在它的服务器后面。

Cloudflare WARP 是该公司推出的一款面向大众的免费网络加速与隐私保护服务（它的官方手机 App 叫 1.1.1.1）。

  1. 它的底层技术：WireGuard 协议
    传统的机场节点（如 Shadowsocks, Vless, Trojan）属于代理（Proxy）。而 WARP 在底层使用的是 WireGuard 协议，这是一种现代、极速且高度加密的 VPN 协议。

  2. 为什么它能完美解锁 Gemini API？（核心原因）
    我的机场节点之所以被 Gemini 封锁，是因为机房 IP 被万人共用，且地理位置特征明显。而 WARP 节点有三大杀手锏：

真正的“大厂白名单”：Cloudflare 和 Google、微软等巨头有极深的网络互连合作（甚至在全球多个数据中心是直接拉光纤物理连接的）。Google 对来自 CF 骨干网的流量非常信任，不容易触发机器人验证。

无限的 IP 资源池：当你通过 WARP 访问 Google 时，CF 的任性之处在于，它会动态分配一个极度干净、未被污染的出口 IP 给你的这次请求。

Anycast（任播）技术：CF 在全球几百个城市都有数据中心。你在国内连接 CF 的节点，它会通过其内部的极速骨干网，将你的流量在最靠近 Google 服务器的国家（如美国、日本、新加坡）送出。在 Google 看来，这笔请求就像是本地居民发出来的一样自然。

配置流程

获取独享的 WARP 节点账密

需要通过网页（如 WireGuard-WARP Generator）或本地工具（如 warp-reg）模拟官方客户端向 Cloudflare 注册，获得一份标准的 WireGuard 配置文件。

最关键的是提取出四个核心参数：PrivateKey、PublicKey、以及内网 Address (IPv4/IPv6)。

这一步其实比想象中的麻烦，找到一个能用的网页工具并不容易。我是用这个搞定的。

https://lanrat.github.io/wireguard-warp-generator/

生成出的大概是这么个东西：

[Interface]
PrivateKey = iEF8bTMc/xi3ZH/nSsnK7VK7a+QmlhbdxyDNMqV1ulw=
Address = 172.16.0.2/32, 2606:4700:110:83e8:1c22:3867:8569:d81b/128
DNS = 1.1.1.1, 1.0.0.1, 2606:4700:4700::1111, 2606:4700:4700::1001
MTU = 1280

[Peer]
PublicKey = bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=
AllowedIPs = 0.0.0.0/0, ::/0
Endpoint = engage.cloudflareclient.com:2408

在 Clash Verge Rev 中配置“全局插队分流”

为了不破坏原本机场的订阅更新，同时让 Gemini 规则拥有最高优先级，不能直接用 proxies 和 rules，必须使用全局功能增强入口。

在 Clash Verge Rev 的订阅页面，如图所示编辑全局拓展覆写配置。

将里面的内容清空，完整填入以下标准的纯英文插队模板（AI写的时候可能会加入一些抽象的Emoji，会触发编码Bug，记得剔除）：

# Profile Enhancement Merge Template for Clash Verge
profile:
  store-selected: true

# 1. 强行在原有节点列表最前面“插队”注入本地 WARP 节点
prepend-proxies:
  - name: "Gemini-WARP-Direct"  # 纯英文命名，防止 Python 库解析报错
    type: wireguard
    server: 162.159.210.66      # 经过测速优选的 CF 边缘节点 IP
    port: 894                   # 避开被封锁的 2408 默认端口，改用 894 魔改端口
    ip: 172.16.0.2              # 对应你 WARP 文件中的 Address IPv4
    ipv6: 2606:4700:110:8183:5d63:78c:cdd3:6599 # 对应你 WARP 文件中的 Address IPv6
    private-key: WEfVpbhRgkhFzcrfbYX18uxR2nXN8fMIeEK2i9SrsF4= # 你的独享私钥
    public-key: bmXOC+F1FxEMF9dyiK2H5/1SUtzH0JuVo51h2wPfgyo=  # 你的独享公钥
    udp: true
    remote-dns-resolve: true

# 2. 强行在原有规则列表最前面“插队”注入分流规则
prepend-rules:
  - DOMAIN-SUFFIX,generativelanguage.googleapis.com,Gemini-WARP-Direct
  - DOMAIN-KEYWORD,ai.google,Gemini-WARP-Direct
  - DOMAIN-SUFFIX,aistudio.google.com,Gemini-WARP-Direct
  - DOMAIN-KEYWORD,gemini,Gemini-WARP-Direct

这里的 ipv4 和 ipv6 对应生成文件中的 Address 部分，server 也不需要专门去测速，填入这个通用的就可以了，偶尔调用一次API 并不需要追求过快的速度，至少目前还不需要。
